# Состояние системы можно переносить при поочерёдной замене всех компонентов

## Идея

В компонентной ОС можно стремиться к **непрерывной работе без перезагрузки**, последовательно заменяя модули, передавая состояние и перенаправляя обращения на новую реализацию. Это относится не только к драйверам и файловым службам, но потенциально и к минимальному ядру, включая механизм, управляющий собственными обновлениями.

Новый модуль подготавливается и проверяется; старый достигает безопасной точки (quiescence), передаёт либо синхронизирует состояние; обращения атомарно переключаются. Предыдущую версию можно удерживать для отката, пока откат остаётся безопасным. В отдельных случаях старый и новый код некоторое время существуют параллельно и постепенно переводят клиентов.

## Контракты жизненного цикла

Наряду с функциональным контрактом нужны:
- протокол миграции состояния, включая открытые файлы, соединения, блокировки, таймеры;
- условия безопасной замены (safe points) и правила маршрутизации уже начатых операций;
- проверка совместимости состояний/версий и согласованное обновление зависимых компонентов;
- явная семантика отката, включая необратимые изменения внешнего мира.

## Самозамена ядра

В принципе обновляющий компонент U1 может подготовить U2, передать ему управление и быть выгружен. Следующий компонент обновляет U2. Однако часть низкоуровневого механизма перехода должна оставаться работоспособной на каждом шаге; временный переходный код, барьеры для всех CPU, атомарная смена обработчиков прерываний и согласование таблиц памяти могут потребовать кратких пауз.

## Уровень обоснования

Это исследовательская гипотеза об общей архитектуре, **не доказательство**, что любую модификацию ядра можно применить без перезагрузки. Аналоги: MINIX 3 Live Update для служб (не всего ядра), K42 для некоторых объектов ядра, Linux Livepatch для ограниченного класса изменений, Erlang/BEAM hot code loading на уровне VM. Малое ядро не означает, что оно никогда не нуждается в обновлении.
