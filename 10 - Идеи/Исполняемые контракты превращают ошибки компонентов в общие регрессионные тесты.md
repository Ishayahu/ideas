# Исполняемые контракты превращают ошибки компонентов в общие регрессионные тесты

## Принцип

Если каждая реализация подсистемы обязана соблюдать **общий контракт поведения**, то проверка соответствия не должна писаться заново для каждой реализации. Любая обнаруженная ошибка может выявить нарушение существующего инварианта или пробел спецификации; тест и, при необходимости, новая версия контракта после этого распространяются на всю экосистему реализаций.

Контракт описывает не только сигнатуры: семантику операций, ошибки, порядок, конкурентность, гарантии персистентности, ограничения ресурсов, версионирование и поведение при сбоях. Проверки могут включать примеры, property-based testing, fuzzing, моделирование отказов и формальные свойства.

## Следствие

Развитие альтернативных реализаций создаёт обратную связь: больше реализаций → больше выявленных граничных случаев → лучше общая спецификация и набор тестов → дешевле проверка будущих реализаций. Возможен differential testing независимых компонентов.

## Пределы

Прохождение тестов не доказывает корректность. Новые тесты предотвращают повторение известного сценария лишь при обязательном выполнении тестов. Если контракты неполны, их независимо корректные реализации могут вместе нарушить системные свойства. Поэтому интеграционные, производительные и долговременные испытания всё равно нужны.

Существующие аналоги: xfstests для файловых систем и Web Platform Tests для веб-движков.
